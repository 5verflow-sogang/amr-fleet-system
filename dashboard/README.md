# dashboard

관제 대시보드 + 직원 호출. 시연 영상에서 관제가 무엇을 판단했고 그래서 무엇이 나아졌는지를 대시보드만 봐도 알 수 있게 한다.
화면·문구·동작은 「관제 대시보드 개발 명세서」를 따른다.

- ROS 패키지가 아니다. `COLCON_IGNORE`로 colcon 빌드에서 제외된다.
- `index.html` 한 장이다. 외부 라이브러리 없이 `rosbridge_server`(WebSocket) 프로토콜을 직접 쓴다. 대시보드 코드가 ROS 노드를 직접 import하지 않는다.
- 필요한 토픽은 [docs/api.md](../docs/api.md)의 인터페이스만 사용한다. 대시보드 전용 데이터가 필요하면 `amr_msgs`에 메시지를 추가하는 절차를 따른다.
- 시계열 KPI는 Prometheus/Grafana(`docker/grafana/`)가 담당하므로, 이 대시보드는 지도 위 로봇 위치·상태·작업·알림처럼 Grafana로 표현하기 어려운 화면에 집중한다.

## 실행

```bash
docker compose build                                   # rosbridge_server가 들어간 이미지 (amr_bringup exec_depend)
docker compose up -d fleet
FAKE_ROBOTS_CONFIG=fake_robots_restaurant.yaml docker compose --profile fake up -d fake-robots   # 식당 위치 모의 로봇 5대
docker compose --profile dashboard up -d
# 브라우저: http://localhost:8080
```

`dashboard` 서비스는 host 네트워크에서 화면(8081)과 rosbridge(9091)를 열고, `dashboard-proxy`가 호스트의 8080·9090으로
중계한다(macOS·Windows Docker Desktop은 host 네트워크 포트가 호스트에 열리지 않는다. `gui`·`gui-proxy`와 같은 방식).
화면은 1280×720 고정이고 어두운 바탕이다(스크린·영상에서 밝기가 날아가도 글자가 보이게). 녹화는 브라우저 창을 1280×720으로 두고 2배로 받는다.

## 화면

왼쪽에 지도(1 m = 32 px), 오른쪽에 관제 판단·작업 순서·호출, 맨 아래 한 줄에 로봇 5대가 있다.

| 영역 | 내용 |
|---|---|
| 상단 바 | 푸드코트 로봇 관제, "집계 12:07 ~ 지금"(숫자 칸이 세기 시작한 시각, 페이지를 연 때), 시각, 연결 상태 |
| 숫자 칸 | 홀 투입("3분" 그래프, 최소 대수), 최장 대기(배정 전 작업), 안전 정지, 완료(서빙·회수). 칸에는 이름과 숫자만 두고 세는 범위는 상단 바 한 곳에 |
| 지도 | 로봇 위치·상태·가는 방향, 혼잡 구역("혼잡 N명" 이름표, 지도 오른쪽 위 "혼잡 발생"/"혼잡 없음"), 경로(없으면 목적지까지 점선), 배정 후보 고리, 고른 테이블 |
| 관제 판단 | 방금 내린 판단 1건: 결정·작업·근거 (아래 문구 템플릿) |
| 작업 순서 | 로봇을 기다리는 작업(처리 순서대로)과 방금 배정된 작업(5초). 제목 오른쪽은 늘 "대기 N건"(0건 포함). 대기 막대는 1분에 꽉 찬다. 칸에 다 안 들어가면 마지막 줄이 "외 N건" |
| 로봇 | 5대의 상태·가는 곳·배터리(5칸, 한 칸 20%), 도움이 필요한 로봇 수. 충전을 마치고 대기 자리로 가는 서버 작업(`TYPE_RETURN`)은 칩 "복귀"로만 보인다 |
| 호출 | 테이블을 골라 빈 그릇 회수, 음식 서빙(누르면 매장 5개가 펼쳐진다). 두 버튼은 테이블을 고르기 전에도 늘 보인다 |

로봇·작업 순서 줄·관제 판단을 누르면 로봇 창·작업 창이, 홀 투입 칸을 누르면 5대 배터리 창(세로 막대·이름·%)이 뜬다.
색은 평소 회색, 관제가 방금 판단한 것 파랑, 직원이 누르는 것(테이블·호출 버튼·고른 테이블) 하늘색, 충전 주황, 혼잡·문제만 빨강이다.
작업은 어디서나 같은 이름표(서빙·회수·충전)로 보인다.

**지도**는 실내 지도 앱(Mappedin)의 2D 보기를 따른다. 바닥·벽·가구·테이블·장소 이름은 회색 한 계열로 조용하게 두고, 위 색은 상태에만 쓴다.
테이블은 누르는 대상이라 가구보다 밝다. 층 순서(앞 → 뒤)는 로봇 > 혼잡 이름표 > 장소 이름·테이블 번호 > 경로 > 혼잡 칠 > 가구 > 바닥이다.
혼잡 이름표는 구역 안에서 테이블·글자·로봇을 가장 덜 가리는 자리에 놓고, 경로는 글자 자리를 비우고 그려 글자를 지나가지 않는다.

### 문구 템플릿

**작업 단계와 로봇 상태는 2글자 명사 하나.** 작업 창 단계와 로봇 칩이 같은 말을 쓰고, 칩 아래 줄에 그 단계의 장소가 나온다.

| 작업 | 단계 |
|---|---|
| 서빙·회수 | 요청 · 배정 · 이동 · 픽업 · 운반 · 전달 · 완료 |
| 충전 | 요청 · 배정 · 이동(주황, 충전소) · 충전 · 완료 |
| 그 밖의 칩 | 대기, 복귀(대기 자리), 문제 상태(안전 정지·비상 정지·오류·연결 끊김) |

**관제 판단은 결정 / 작업 / 근거 세 줄.** 결정은 `N호 배정` 또는 `{작업} N순위`, 작업은 이름표 + 경로, 근거는 아래 이름 중 하나(필요하면 ` · 수치`).

| 근거 | 쓰는 때 | 예 |
|---|---|---|
| 최단 거리 | 가장 가까운 로봇 배정 | 1호 배정 / 최단 거리 |
| 혼잡 회피 | 더 가까운 로봇이 있지만 덜 혼잡한 길로 갈 로봇 배정 (아래 표에 거리·혼잡 구간) | 3호 배정 / 혼잡 회피 |
| 대기 로봇 1대 | 고를 로봇이 한 대뿐 | 2호 배정 / 대기 로봇 1대 |
| 회수 우선 | 새 회수가 기다리던 서빙 앞에 섬 | 회수 1순위 / 회수 우선 |
| 요청 순서 | 회수 우선을 끈 경우(`collect_priority=100`) | 회수 5순위 / 요청 순서 |
| 장기 대기 | 오래 기다린 서빙이 새 회수보다 앞에 섬(aging). 수치는 그 서빙의 대기 시간(m:ss) | 서빙 1순위 / 장기 대기 · 1:16 |
| 교대 충전 | 충전 배정. 수치는 이 로봇이 빠진 뒤 홀에 남는 대수 | 2호 배정 / 교대 충전 · 홀 투입 3대 |

**도움이 필요한 로봇은 "이유 · 지난 시간(m:ss)"과 할 일.** 로봇 창 빨간 상자에 나온다. 안전 정지는 30초가 지나야 도움 필요로 보고 할 일을 붙인다.

| 상태 (칩) | 이유 | 할 일 |
|---|---|---|
| 안전 정지 | 장애물 감지 (`SafetyStatus` reason 1·2) | 로봇 앞 통로를 확보하세요 |
| 안전 정지 | 센서 이상 (reason 4) | 로봇 센서를 점검하세요 |
| 안전 정지 · 비상 정지 | 비상 버튼 (reason 3, `MODE_ESTOP`) | 현장에서 해제하세요 |
| 오류 | 오류 | 현장에서 로봇을 점검하세요 |
| 연결 끊김 | 연결 끊김 (상태가 5초 넘게 안 옴) | 로봇 전원과 네트워크를 점검하세요 |

**그 밖의 문구.** 지난 시간은 어디서나 m:ss(작업 순서, 최장 대기, 관제 판단, 빨간 상자). 호출 뒤 알림은 "회수 요청 완료 · 3번 테이블", "서빙 요청 완료 · 한식 → 3번 테이블", 못 보내면 "요청 실패 · 연결되면 다시 누르세요". 연결은 "연결됨" / "연결 끊김 · 재연결 중". 배터리는 칸과 %만 쓰고 남은 시간 추정은 보이지 않는다(충전 중 주황, 20% 아래 빨강).

## 주소 옵션

| 옵션 | 뜻 | 기본값 | 쓰는 곳 |
|---|---|---|---|
| `ws` | rosbridge 주소. `off`면 연결하지 않는다(시험) | `ws://<페이지 호스트>:9090` | 공통 |
| `collect_priority` | 회수 `priority` | 200 | 2 1막 끔: 100 ("회수 N순위 · 요청 순서") |
| `collect_type` | 회수 `task_type`. 0이면 `TYPE_DELIVERY`로 보내고 `task_id` 접두사 `collect_`로 구분한다 | 3 (`TYPE_COLLECT`, #302) | 공통 |
| `aging_rate` | 작업 순서 계산. 서버 `assignment.aging_rate`와 같게 | 0 | 2 2막 켬: 1.667 ("서빙 1순위 · 장기 대기") |
| `clock` | 시뮬레이션 0초에 보일 시각 (`12:07:00`). 숫자 칸의 "12:07부터"도 이 시각 | 없음 | 장면마다 스토리 시각 |
| `min_hall` | 홀 투입 최소 대수 (숫자 옆 "최소 3대", 그래프에서 그 아래는 옅은 띠·빨간 선, 모자라면 숫자 빨강) | 없음 | 3: 3 |

## 받는 토픽

| 토픽 | 쓰는 곳 |
|---|---|
| `/fleet/robot_states` | 지도, 로봇, 숫자 칸, 배터리 창 |
| `/fleet/task_table` | 작업 순서, 관제 판단, 호출 중복 막기, 로봇 칩(충전·복귀) |
| `/fleet/task_status` | 로봇 칩 단계, 완료(서빙·회수), 작업 창 시각 |
| `/fleet/congestion` | 혼잡 구역 |
| `/amr_0N/safety/status` | 안전 정지 |
| `/clock` | 시각 (없으면 브라우저 시각. 처음 오면 시간 기준을 시뮬레이션 시간으로 바꾼다) |
| `/fleet/assignment_decisions` | 배정 이유와 후보 비교 (메시지 `amr_msgs/AssignmentDecision`이 생기면 바로 쓴다. 없으면 큰 글씨와 작업 줄만) |
| `/amr_0N/plan` | 경로 (없으면 목적지까지 점선) |

보내는 토픽은 `/fleet/task_requests`(`amr_msgs/Task`, api.md 4-6절) 하나다. `task_id`는 `collect_`·`delivery_` + UUID다.

## 시험

```bash
pip install playwright && playwright install chromium
python3 dashboard/test/check_ui.py --shots dashboard/test/out/shots   # ROS 없이 명세 3장 완료 기준 + 5장 문구 규칙, 지도 겹침 (49개), 시연 장면 13장
python3 dashboard/test/check_stack.py --url http://localhost:8080 \
  --restart "docker compose --profile dashboard restart dashboard"   # 실제 스택 (위 실행 뒤). 호출 → 배정, 다시 연결
```

`check_ui.py`는 `window.dashTest.feed(topic, msg)`로 메시지를 넣고 Playwright 가짜 시계로 시간을 돌린다(1분 넘은 대기, 30초 넘은
안전 정지 등을 실제로 기다리지 않고 본다). `check_stack.py`는 모의 로봇(`fake_robot_node`: 시뮬레이터 없이 위치만 계산하는 가짜 로봇)으로
호출부터 완료까지 확인한다. 모의 로봇은 배터리 100% 고정이고 안전 상태를 보내지 않으므로 배터리·안전 정지는 `check_ui.py`가 맡는다.
