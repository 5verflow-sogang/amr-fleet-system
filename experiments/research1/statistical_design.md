# 연구 1 통계 설계 (반복 수, 조건 배치, 검정, 전환 임계점 판정)

[명세서 3장](../../docs/project-spec.md) 연구 1의 실험을 통계적으로 어떻게 돌리고 판정할지 정한다. 실험(P2, 10/27~) 전에 고정한다. 담당: 민지(통계), 하연(연구 1 주저자·실험).

> 상태: 초안 (10/6). N은 Before 데이터(10/11)의 실행 간 표준편차를 보고 확정한다(3절).

## 1. 무엇을 주장하려는가

| 주장 | 필요한 결과 | 판정 방식 |
| --- | --- | --- |
| C1 Before 기준값 | 지연 0 ms·100 ms, 중앙집중, 5대의 처리량·완료 시간·P95/P99 지연 | 평균과 95% CI |
| C2 성능 곡선 | 지연·손실·대수를 바꿀 때 세 비교군(중앙집중·분산·하이브리드)의 지표 | 조건마다 평균·CI, 비교군 차이의 CI |
| C3 전환 임계점 | 분산이 중앙집중보다 나아지는 지연(·손실) 값. 주 지표는 **평균 작업 완료 시간** (5절) | 임계점의 부트스트랩 CI |
| C4 KPI 통과 | 스펙 조건(100 ms, 중앙집중, 5대)에서 평균 응답 200 ms 이내(**최대도 함께 보고**, 원 명세 "평균/최대"), CPU 80% 이하 | CI 상한 기준 (하네스 판정과 같음) |
| C5 After 개선 | QoS·DDS 벤더 튜닝 전후, **스펙 조건(과 지연 0 ms)에서만** 개선폭 | 짝지은 비율의 CI |

- C5를 지연 조건 전체로 넓혀 "튜닝이 임계점을 얼마나 옮기는지"까지 보면 실험량이 두 배가 되므로 하지 않는다(#85 하연 리뷰).

## 2. 원칙

- **분석 단위는 실행(run)이다.** 한 실행 안의 메시지·작업은 같은 서버·같은 네트워크 상태를 공유해 서로 독립이 아니다. 실행마다 지표를 하나로 요약하고(예: 그 실행의 처리량, P95 지연), 실행들로 신뢰구간을 낸다. 하네스 합의(#33 "지연 신뢰구간은 실행 단위 부트스트랩")와 같다.
- **공통 난수(짝지은 설계)**: 반복 k는 모든 비교군·조건에서 같은 seed를 쓴다(작업 일정 `tasks.json`, 손실 난수). 같은 작업 일정에서 비교군만 바꾸므로 일정 운에 따른 차이가 빠지고, 비교군 차이를 seed k끼리 빼서 분산을 줄인다.
- **seed 규칙**(하네스 README): 본 실험 1~N, 예비·튜닝 1001~. 예비 실험 seed로 본 결과를 보고하지 않는다.
- **분석 계획 사전 고정**: 지표 정의, N, 조건 목록, 판정 기준을 이 문서로 먼저 고정하고 본 실험을 돌린다. 바꾸면 이유와 바꾸기 전 결과를 함께 남긴다.
- **실패 실행 구분**: 하네스가 기동 실패(`outcome` ≠ `completed`)로 표시한 실행은 같은 seed로 다시 돌린다(하네스 `--max-attempts`). 교착·충돌·시간 초과는 실험 결과(종속변수)이므로 빼지 않는다.

## 3. 반복 수 N

**기본 N = 10, 최소 5.** Before 데이터(10/11)로 아래 식을 계산해 확정한다.

- 평균의 CI 반폭을 평균의 ±5% 이내로: n ≈ (1.96 · s / (0.05 · 평균))²
- 두 비교군 차이 δ를 짝지은 설계로 검출(유의수준 0.05, 검정력 0.8): n ≈ (1.96 + 0.84)² · s_d² / δ², s_d는 seed끼리 뺀 차이의 표준편차
- 짝지은 설계라 s_d가 s보다 작다(같은 작업 일정). 예비로 s_d를 재서 쓴다.
- 부트스트랩은 표본이 적으면 구간이 약간 좁아지므로 N < 10이면 t 구간도 함께 보고하고 넓은 쪽으로 판정한다.

**실행당 표본 수와 꼬리 지연(P95/P99)**: 기본 시나리오(작업 60건, 약 10분, 5대)에서

| 메시지 | 실행당 개수 | 실행 하나로 낼 수 있는 것 |
| --- | --- | --- |
| heartbeat (5 Hz × 5대) | 약 15,000 | P95·P99 모두 안정 |
| task_table (1 Hz × 5대) | 약 3,000 | P95·P99 |
| task_assignments·Ack (작업 수) | 약 60 | 평균·중앙값. P95는 상위 3번째 값이라 불안정, **P99는 불가** |

- P99는 실행마다 꼬리 표본이 최소 10개는 있어야 한다(P99면 약 1,000건 이상). 할당·Ack 지연의 P99는 실행 단위로 내지 않고, (a) heartbeat·task_table 같은 주기 메시지로 링크 지연 P99를 보고, (b) 할당 지연은 평균·P95까지만 실행 단위로 낸다. 할당 P99가 꼭 필요하면 작업 수를 늘린 시나리오(예: 300건)를 따로 둔다.
- 여러 실행의 메시지를 합쳐 P99를 그리는 것은 그림(분포 모양)에만 쓰고, CI는 실행 단위로 낸다.

## 4. 조건 배치

명세서 독립변수를 모두 곱하면 지연 5 × 손실 4(0·1·5·10%) × 대수 4 × 비교군 3 = 240조건이다. N = 10, 실행당 약 15분이면 600시간이라 할 수 없다. 그래서 **스펙 조건(100 ms, 손실 0%, 5대)을 중심으로 한 변수씩 바꾼다.**

| 단계 | 바꾸는 것 | 고정 | 조건 수 (× 비교군 3) | 목적 |
| --- | --- | --- | --- | --- |
| A 지연 | 0·50·100·200·500 ms | 손실 0%, 5대 | 5 → 15 | C1, C2, C3 지연 임계점 |
| B 손실 | 0·1·5·10% | 100 ms, 5대 | 4 → 12 (100 ms·0%는 A와 공유) | C2, 손실 임계점 |
| C 대수 | 3·5·7·10대 (RTF 확인 후 확정) | 100 ms, 0% | 4 → 12 (5대는 A와 공유) | 스케일 한계 |
| D 세분 | A에서 임계점이 걸친 두 지연 사이 2점 | A와 같음 | 2 → 6 | C3 임계점 좁히기 (5절) |
| E 교호 확인 | 지연 200 ms × 손실 5% 1점 | 5대 | 1 → 3 | 지연·손실이 겹칠 때 따로 볼 때와 다른지 확인 |

- 중복을 빼면 약 15조건 × 비교군 3 = 45조건, N = 10이면 450실행. 실행당 15분이면 약 113시간이다. GCP 서울 리전 N2D 한도가 16 vCPU라 `n2d-standard-16` 러너는 동시에 1대뿐이어서 **약 5일**이 걸린다(#85 하연).
- 줄이는 안: 임계점이 걸리는 A·D·E는 N = 10, B·C는 N = 5로 하면 A·D·E 24조건 × 10 + B·C 새 조건 18 × 5 = 330실행, 약 83시간(3.5일). Before 데이터로 N을 재계산한 뒤 고른다.
- **대수(C)는 실시간으로 도는지 먼저 확인한다.** 카메라를 끈 5대에서 RTF 1.0은 쟀지만 7·10대는 재지 않았다. RTF가 1 아래로 떨어지면 실제 시간으로 재는 응답 시간이 왜곡되므로, 예비로 대수별 RTF를 재고 RTF ≥ 0.95인 대수까지만 넣는다. 못 넣은 대수는 한계로 보고한다. 실행마다 RTF는 `meta.json`에 남는다.
- 한 변수씩 바꾸는 배치는 교호작용(지연과 손실이 같이 클 때의 비선형)을 놓친다. E로 한 점만 확인하고, 크면 한계로 적는다.
- 실행 순서는 조건을 섞어(무작위 순서) 돌린다. 시간대·러너 차이가 특정 조건에 몰리지 않게 하기 위해서다. 러너는 `meta.json`의 `host`로 기록하고, 러너 간 차이가 크면 러너를 블록으로 보고 분석한다.

## 5. 검정과 임계점 판정

**지표 (실행마다 하나)**: 평균 작업 완료 시간, 처리량(완료 작업/분), 교착 발생 수, 충돌 건수, 총 이동 거리, 링크 지연 P95·P99, 할당 응답 시간 평균·P95·최대, CPU 최대.

**처리량은 기본 시나리오에서 주 지표로 쓰지 않는다.** 작업 생성기는 10초마다 정해진 일정대로 작업을 넣어서, 로봇이 따라가는 한 처리량은 투입 속도(분당 6건)에 묶이고 지연이 커져도 거의 변하지 않는다(#85 하연). 그래서 임계점·급락 판정은 평균 작업 완료 시간으로 한다. 처리량으로 보려면 투입을 로봇 처리 능력보다 빠르게 하는 포화 시나리오(작업 간격을 줄인 시나리오)를 따로 둔다.

**비교군 비교 (C2)**: 같은 조건·같은 seed k끼리 차이 Δ_k = (분산 − 중앙집중) 등을 내고, Δ_k를 복원 추출하는 부트스트랩 95% CI(10,000회). 보조로 Wilcoxon 부호순위 검정(정규성 가정 없음, N이 작음). 한 단계 안의 여러 조건 비교는 Holm 보정.

**전환 임계점 (C3)**: 평균 작업 완료 시간(작을수록 좋음) 기준으로

1. 지연 d마다 Δ(d) = 중앙집중 완료 시간 − 분산 완료 시간 (양수면 분산이 낫다).
2. 이산 판정: Δ(d)의 CI 하한 > 0이 되는 가장 작은 d. "100~200 ms 사이"처럼 격자 구간으로 보고한다.
3. 연속 추정: 조건마다 실행을 복원 추출해 Δ(d)를 다시 계산하고, 인접 격자점 사이를 직선으로 이어 Δ(d) = 0이 되는 d*를 구한다. 이를 10,000번 반복한 d*의 2.5·97.5 백분위를 d*의 95% CI로 보고한다. 교차가 없으면(Δ가 끝까지 음수) "500 ms까지 전환점 없음"으로 보고한다.
4. D 단계로 교차 구간 안에 점을 더 넣어 CI를 좁힌다. 이때 seed는 같은 1~N을 쓴다.

**하이브리드 폴백 트리거**: 하이브리드는 실행 중 지연을 *관측*해서 전환해야 하므로, 주입 지연 d*를 관측 가능한 값으로 바꿔 제시한다. 같은 실행의 Ack 왕복시간(`ack_rtt_ms`, D8에 따라 주입 지연 1회 + 1홉) P95와 주입 지연의 관계(fleet_fake 스모크: 주입 200 ms → Ack 203 ms)로 d*를 "Ack P95 기준 임계값"으로 옮긴다.

**성능 급락 지점**: 명세서 3-3절 4번의 "처리량이 급락하는 지점"은 기본 시나리오에서 처리량이 움직이지 않으므로, 중앙집중 평균 완료 시간이 지연 0 ms 기준보다 10% 넘게 늘어나는 가장 작은 d로 정의한다(비율의 CI 하한 > 1.10). 10%는 초안이고 Before 데이터의 실행 간 변동을 보고 정한다. 포화 시나리오를 두면 처리량이 0 ms 대비 90% 아래로 떨어지는 지점도 함께 본다.

**After 개선 (C5)**: 튜닝 전후를 같은 seed k로 짝지어 개선 비율 r_k = (전 − 후)/전(지연·완료 시간) 또는 (후 − 전)/전(처리량)의 부트스트랩 CI. "P99 지연 x% 감소 (95% CI a~b%)"로 보고한다.

## 6. 보고 형식

- 표: 조건 × 비교군마다 평균, 95% CI, N, 실패(기동) 수
- 그림: 지연(가로) – 처리량(세로) 곡선, 비교군별 선과 CI 띠, 임계점 d*와 그 CI를 세로 띠로
- 원자료(`results/<run_id>/`)와 분석 스크립트를 함께 남겨 다시 만들 수 있게 한다

## 7. 도구

- 반복 실행·결과 폴더·실행 단위 CI: 하네스 v1(#77). 조건은 `--set delay_ms=… --set loss_pct=… --label …`
- 비교군 차이·임계점 부트스트랩·Holm: 하네스 `summarize.py`를 확장한다(짝지은 차이, 격자 보간 임계점). 연구 2 분석 스크립트(#82)의 짝지은 부트스트랩과 같은 방식이다
- 실제 로봇 스택 시나리오(응답 시간·처리량)는 하네스에 시나리오를 추가한다. `fleet_fake`는 Fleet 계층 지연·손실·Ack만 잰다
