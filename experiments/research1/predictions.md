## 연구 1 사전 예측 (10/17, 하연)

결과를 보기 전에 예측을 커밋해 둔다. 이 파일의 커밋 시각이 등록 시각이다. 예측이 틀리면 틀린 대로 보고한다.

- P2(짧은 작업)·P3(끊기면 멈춤)은 실행 전에 커밋한다

### 1. 모델: 중앙 관제가 버티는 이유

포화 상태(대기열이 늘 차 있음)에서 로봇이 작업을 끝내면 서버가 바로 다음 명령을 보낸다. 서버 → 로봇 메시지가 확률 p로 사라질 때

- 서버는 `resend.interval_s`(r = 1초)마다 다시 보낸다. 재전송 `max_resends`(k)번을 다 쓰면 작업을 대기열로 되돌리는데, 그 로봇은 그때도 비어 있어 같은 조건으로 바로 다시 맡는다(새 명령). 그래서 **포기 후 재배정이 재전송과 같은 일을 한다**
- 로봇이 명령을 받기까지 더 기다리는 시간의 기댓값은 k와 상관없이

  **W = r · p / (1 − p)**

- 작업 수행 시간 T, 장애 없을 때 작업 사이 대기 g0이면 처리량 비율은

  **처리량(p) / 처리량(0) ≈ (T + g0) / (T + g0 + W)**

#### 지금까지 결과와 대조 (사후, 참고)

포화 기본 시나리오(T ≈ 59초, g0 = 0.53초, 10회)

#### P2. 작업이 짧으면 같은 손실에서 더 많이 잃는다

`--set robot_speed_mps=3 --set task_interval_s=3 --set task_count=200` (수행 약 21초, 투입 20건/분 > 처리 약 14건/분이라 포화 유지). 조건: 장애 없음 / 손실 50% / 손실 70%, seed 1~10.

- 판정: T와 g0을 장애 없음 실행에서 다시 재고 위 식으로 다시 계산한 예측값이, 같은 seed끼리 짝지은 완료 작업 변화의 95% CI 안에 있으면 맞은 것으로 본다. 작업 사이 대기 증가가 W(1.0초, 2.33초)와 ±0.3초 안이어야 한다

#### P3. 끊기면 멈추면 끊긴 로봇의 몫을 크게 잃는다

### P4. 가동률 80%: 처리량은 그대로, 완료 시간 증가는 비포화와 포화 사이

- 손실 70%여도 처리 능력은 4.0 × (1 − 3.8%) ≈ 3.85건/분 > 투입 3.2건/분이라 대기열이 무한히 쌓이지 않는다
- 예측: 완료 작업 수는 장애 없음과 같다 (짝지은 차이 95% CI가 0을 포함)
- 예측: 평균 완료 시간 증가는 비포화(가동 약 50%)와 포화 사이
  - 손실 70%: +3.4%(비포화) ~ +6.4%(포화)
  - 단절 30초: +2.4%(비포화) ~ +4.6%(포화)
- 판정: 평균 완료 시간 증가의 점 추정이 위 구간 안이면 맞음

### P5. 몰림 정도: 단절 시간 비율이 같아도 끊김이 짧으면 거의 손해가 없다

amr_03만 끊되 끊김 비율은 50%로 같게 하고 길이만 바꾼다(주기 = 끊김 × 2, 40초부터, delay 모드).
조건: 3초/6초, 10초/20초 (30초/60초는 `central_bo30_r3`로 이미 있음).

- 서버는 1초 간격으로 6번(약 6초) 다시 보내고, 끊김이 끝나면 붙잡혔던 명령이 바로 도착한다. 명령이 끊긴 구간에 걸릴 확률 0.5 × 남은 끊김 평균 L/2이므로, amr_03이 명령을 받기까지 더 기다리는 시간 ≈ L/4 (재시도 창 6초보다 짧을 때)
- 예측: amr_03 작업 사이 대기 증가 **3초 끊김 약 0.75초, 10초 끊김 약 2.5초** (±50%). 30초 끊김은 재시도 창을 넘어 7.8초(실측)
- 예측: 함대 완료 작업 변화는 3초·10초 모두 95% CI가 0을 포함 (30초는 −0.9건으로 유의)
- 판정: 위 두 가지가 모두 맞으면 "독립 손실은 재시도 간격, 재시도 창(약 6초)보다 긴 끊김은 단절 로봇 정책"이라는 적용 범위 구분이 맞은 것으로 본다

### P6. 허가 지점 대기: 멈춤과 계속 사이, 대략 가운데 (10/18 등록)

`--set pause_on_link_loss_s=2 --set pause_mode=leg` + 단절 30초(amr_03, 40초부터 60초마다). 끊긴 동안 지금 구간(선반까지·목적지까지·싣기·내리기)은
마저 하고 다음 구간 앞에서 기다린다. 교통 통제가 있는 현장(허가 지점에서 서버 허가가 필요)을 흉내 낸 정책이다 (VDA 5050 확정 구간).

- 이동 구간은 평균 약 28초(작업 약 59초 = 이동 2구간 + 싣기·내리기 1초씩)라, 끊긴 시점에 남은 구간이 평균 약 14초다. 그만큼 더 일하고 나머지(약 14초)를 기다리므로 멈춤 정책 손해의 절반쯤을 되찾는다
- 예측: amr_03 완료 작업 **약 5.8건(±1)** (멈춤 4.0건, 계속 7.2건, 단절 없음 7.6건), 함대 완료 **약 38.3건(±1.5)**, 평균 완료 시간 변화 **+10~15%** (멈춤 +21.7%, 계속 +4.6%)
- 판정: amr_03 완료 작업과 함대 완료 작업의 점 추정이 위 범위 안이면 맞음

### P7. 재시도 간격을 늘리면 같은 손실에서 비용이 그만큼 커진다 (10/18 등록)

`--set resend_interval_s=3` + 손실 50% / 70%, 포화 기본 시나리오(60초 작업). 비교 기준은 간격 1초인 `central_loss50`·`central_loss70`과 장애 없음 `central_d0`.

- 식 (1) W = r·p/(1−p): r = 3초이면 **손실 50% 3.0초, 손실 70% 7.0초** (1초 간격의 3배)
- 식 (2) T + g0 ≈ 59.5초: 처리량 변화 **손실 50% −4.8%, 손실 70% −10.5%** (장애 없음 대비)
- 보조 예측(오차 ±40%): 평균 완료 시간 변화는 지금까지 W 1초당 약 2.7%였으므로 손실 50% 약 +8%, 손실 70% 약 +19% (급락 기준을 넘음)
- 판정: 작업 사이 대기 증가가 예측의 ±20% 안이고, 처리량 변화 예측값이 짝지은 95% CI 안이면 맞음

### P8. 양방향 끊김에서는 "받은 일 계속"도 잘못된 회수로 이득이 줄어든다 (10/18 등록)

`--set relay_uplink=true` + 단절 30초(amr_03, 40초부터 60초마다, delay 모드). 로봇 → 서버(상태 보고·작업 상태·확인)도 같은 일정으로 끊긴다.
조건: 받은 일 계속(기본) / 끊기면 멈춤(`pause_on_link_loss_s=2`). 비교 기준은 한 방향 끊김(`central_bo30_r3`, `central_bo30_r3_pause`).

- 서버는 amr_03의 상태 보고가 5초(`reclaim_timeout_s`) 끊기면 작업을 회수해 다른 로봇에게 준다. 끊김 30초마다 약 25초 동안 회수 상태가 된다
- 받은 일 계속: amr_03은 회수된 작업을 계속 하므로 **같은 작업을 두 로봇이 한다(중복 실행이 처음으로 생긴다, 실행당 수 건)**. 연결이 돌아오면 먼저 수락한 amr_03이 주인이 되어 다시 맡은 로봇이 물러난다(104). 그 로봇의 시간이 낭비되므로 완료 시간 증가가 한 방향(+4.6%)보다 **커진다**
- 끊기면 멈춤: 회수된 작업을 다른 로봇이 하고, 연결이 돌아오면 amr_03은 먼저 수락했으므로 주인으로 되돌아온다. 손해는 한 방향 멈춤(+21.7%)보다 **작아진다**(회수로 일부 메워짐)
- 판정: 받은 일 계속에서 중복 실행이 0보다 크고 완료 시간 증가가 +4.6%보다 크면, 그리고 멈춤의 완료 시간 증가가 +21.7%보다 작으면 맞음. 두 정책의 차이(멈춤 − 계속)가 한 방향보다 줄어드는지도 본다

### P9. 회수 기준을 단절보다 길게 하면 양방향 단절의 중복 실행과 추가 손해가 사라진다

`--set relay_uplink=true --set reclaim_timeout_s=40` + 단절 30초(amr_03, 40초부터 60초마다, delay 모드), 포화 기본 시나리오.
조건: 받은 일 계속(`central_bo30_r3_up_rc40`) / 끊기면 멈춤(`pause_on_link_loss_s=2`, `central_bo30_r3_up_pause_rc40`).
비교 기준은 회수 5초 양방향(`central_bo30_r3_up` +9.0%, `central_bo30_r3_up_pause` +36.7%)과 한 방향(`central_bo30_r3` +4.6%, `central_bo30_r3_pause` +21.7%), 장애 없음 `central_d0`.

- 회수 40초는 한 번의 단절(30초 + 풀리는 시간 약 1초)보다 길어서 서버가 작업을 회수하지 않는다 → **중복 실행 실행당 평균 0.2건 미만** (5초 회수는 4.2건, 4.7건)
- 회수가 없으면 양방향은 서버가 상태 보고를 못 받는다는 점만 한 방향과 다르므로, 완료 시간 증가는 한 방향 수준으로 돌아온다 → 평균 완료 시간 증가 **계속 0~+7%, 멈춤 +14~+25%** (둘 다 회수 5초의 +9.0%, +36.7%보다 작다)
- 판정: 중복이 위 기준 안이고 두 정책의 평균 완료 시간 점추정이 위 범위 안이면 맞음. 하나라도 벗어나면 "회수 기준이 헛수고의 원인"이라는 설명이 불충분한 것으로 본다

### P10. 하이브리드 전환 기준을 재시도 창보다 길게 하면 손실에서 오탐이 사라진다

`--set fleet_mode=hybrid --set fallback_timeout_s=6` (기본 2초). 조건: 손실 70%(`hybrid_loss70_t6`), 단절 30초(amr_03, 한 방향, `hybrid_bo30_r3_t6`).
비교 기준은 전환 2초의 같은 조건(`hybrid_loss70`: 실행당 전환 109회, `hybrid_bo30_r3`: 10회)과 중앙 `central_loss70`(+6.4%), `central_bo30_r3`(+4.6%).

- heartbeat는 초당 5개이므로 6초는 30개 연속 손실이다. 독립 손실 70%에서 한 로봇이 30개 이상 연속으로 잃는 횟수의 기댓값은 3,100 × 0.3 × 0.7^30 ≈ 0.02이고, 5대면 실행당 약 0.1회다 (2초는 같은 식으로 약 130회, 실측 109회)
  → 손실 70%에서 **실행당 전환 0.5회 미만**
- 전환이 거의 없으니 하이브리드가 중앙과 같아져, 손실 70%의 평균 완료 시간 증가는 중앙(+6.4%)과 ±3점 안 (**+3~+10%**)
- 단절 30초는 6초보다 훨씬 길어 전부 감지한다 → **실행당 전환 9~10회** (단절 10번), 평균 완료 시간 변화 −1~+5%
- 판정: 손실 70%의 전환 횟수와 단절 30초의 전환 횟수가 모두 위 범위 안이면 맞음

### P11. 로봇 10대에서도 손실 비용은 같고, 단절 한 대의 영향은 대수에 반비례한다

`--set num_robots=10 --set task_interval_s=5 --set task_count=120` (처리 능력 약 10건/분보다 투입 12건/분이 많아 포화 유지, 규모 곡선 B안과 같은 설정).
조건: 장애 없음(`n10_d0`) / 손실 70%(`n10_loss70`) / 단절 30초 받은 일 계속(`n10_bo30_r3`, amr_03 한 대) / 단절 30초 + 멈춤(`n10_bo30_r3_pause`). 비교 기준은 같은 N=10의 `n10_d0`.
5대 결과(+6.4%, +4.6%, +21.7%)와 같은 방식으로 비교한다.

- 손실은 모든 로봇의 모든 명령에 독립으로 걸리므로 식 (1)은 대수와 무관 → 작업 사이 대기 증가 **2.33초 ±0.5초**, 평균 완료 시간 증가 **+3~+10%** (5대 +6.4%)
- 단절은 한 대만 걸리므로 영향받는 용량 비율이 1/5에서 1/10으로 준다. 5대의 절반으로 가정하면 받은 일 계속 **0~+5%** (5대 +4.6%), 멈춤 **+6~+16%** (5대 +21.7%)
- 판정: 세 점추정이 각 범위 안이면 맞음. 단절 두 조건이 범위 위쪽으로 벗어나면 "영향이 한 대 비율에 비례한다"는 가정이 틀린 것으로 본다
