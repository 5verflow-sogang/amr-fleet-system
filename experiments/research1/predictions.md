## 1. 모델: 중앙 관제가 버티는 이유

포화 상태(대기열이 늘 차 있음)에서 로봇이 작업을 끝내면 서버가 바로 다음 명령을 보낸다. 서버 → 로봇 메시지가 확률 p로 사라질 때

- 서버는 `resend.interval_s`(r = 1초)마다 다시 보낸다. 재전송 `max_resends`(k)번을 다 쓰면 작업을 대기열로 되돌리는데, 그 로봇은 그때도 비어 있어 같은 조건으로 바로 다시 맡는다(새 명령). 그래서 **포기 후 재배정이 재전송과 같은 일을 한다**
- 로봇이 명령을 받기까지 더 기다리는 시간의 기댓값은 k와 상관없이

  **W = r · p / (1 − p)**

- 작업 수행 시간 T, 장애 없을 때 작업 사이 대기 g0이면 처리량 비율은

  **처리량(p) / 처리량(0) ≈ (T + g0) / (T + g0 + W)**

## 2. 사전 예측

### P1. 재전송 횟수는 처리량을 바꾸지 않는다

`--set loss_pct=50 --set max_resends=0` / `=1` vs `central_loss50`(k = 5), 포화 기본 시나리오, seed 1~10.

- 예측: 세 조건 모두 W ≈ 1.0초. 같은 seed끼리 뺀 완료 작업 차이와 평균 완료 시간 비율의 95% CI가 0(비율은 1)을 포함한다
- 다른 점: k가 작을수록 다시 맡긴 작업 수(`robots` 열 2개 이상)가 늘어난다 (k = 0이면 첫 발송 유실 50%가 모두 재배정)

### P2. 작업이 짧으면 같은 손실에서 더 많이 잃는다

`--set robot_speed_mps=3 --set task_interval_s=3 --set task_count=200` (수행 약 21초, 투입 20건/분 > 처리 약 14건/분이라 포화 유지). 조건: 장애 없음 / 손실 50% / 손실 70%, seed 1~10.

- 예측 (T ≈ 21초, g0 ≈ 0.53초): 처리량 변화 **손실 50% −4.4%, 손실 70% −9.8%** (60초 작업은 −1.7%, −3.8%)
- 판정: T와 g0을 장애 없음 실행에서 다시 재고 위 식으로 다시 계산한 예측값이, 같은 seed끼리 짝지은 완료 작업 변화의 95% CI 안에 있으면 맞은 것으로 본다. 작업 사이 대기 증가가 W(1.0초, 2.33초)와 ±0.3초 안이어야 한다

### P3. 끊기면 멈추면 끊긴 로봇의 몫을 크게 잃는다

`--set pause_on_link_loss_s=2` + 끊김 30초(amr_03, 40초부터 60초마다), 포화 기본 시나리오 vs `central_bo30_r3`(계속 수행).

- 끊길 때마다 약 28초(30초 − 감지 2초) 멈춘다. 실행 620초 중 약 10번이라 amr_03은 실행의 약 45%를 멈춰 있다
- 서버는 amr_03이 살아 있다고 보므로(RobotState는 장애 없음) 멈춘 작업을 회수하지 않는다
- 예측: **amr_03 완료 작업 약 4건(±1)** (계속 수행 7.2건), **함대 완료 작업 약 36.5건(±1.5)** (계속 수행 39.2건, 장애 없음 40.1건)
- 주의: 멈춘 동안에도 RobotState mode는 BUSY라서 가동률(BUSY 비율)로는 비교하지 않고 완료 작업 수로 본다
