# 적재 질량 제동 거리 실험

- 담당: 이진
- 범위: `experiments/payload_braking/` 전용. `src/simulation/amr_description`,
  `src/simulation/amr_gazebo`(지수 패키지)는 건드리지 않았다 — 최소 로봇·월드를
  이 디렉토리 안에 독립적으로 새로 만들었다.

## 1. 목적

1. **Gazebo 시뮬레이션이 적재 질량을 가속·제동에 반영하는지 확인.** 우리 로봇
   스택은 지금 `DiffDrive`(속도 명령, V) 플러그인으로 구동한다 — 속도를
   "명령"하면 물리엔진이 그 속도를 거의 그대로 만들어내는 **속도 소스** 방식이라,
   질량이 바뀌어도 "속도를 낼 수 있는가"에는 영향이 없을 수 있다. 실제로 질량이
   가속·제동에 반영되려면 **힘(토크)으로 명령**하고 그 토크가 현실적인 한계
   안에서 포화돼야 한다 — 그래서 바퀴 조인트를 토크로 직접 명령하는 두 번째
   구동 방식(T, `JointController` 힘 모드)을 만들어 V와 비교했다.
2. **현실적인 모터 사양에서 적재에 따른 제동 거리 차이가 의미 있게 큰지 확인.**
   토크 한계를 임의로 정하지 않고, 아래 2절의 실제 상용 AMR/모터 사양을 참고해
   정했다.

## 2. 모터 사양 근거

| 플랫폼/모터 | 본체 질량 | 적재 질량 | 모터 | 최고 속도 |
| --- | --- | --- | --- | --- |
| Robotnik RB-1 Base | 30 kg | 50 kg | 250 W × 2 | 1.5 m/s |
| Clearpath Jackal | 17 kg | 20 kg | - | 2.0 m/s |
| AgileX Scout Mini | 26 kg | 10 kg | 150 W × 4 | - |
| Waveshare DDSM350 허브모터 | - | - | 정격 1.1 N·m / 최대 3 N·m | - |

**본체 25 kg, 바퀴당 최대 토크 3 N·m으로 정한 이유**: 위 플랫폼들은 본체
17~30 kg 대의 소형 AMR이라 25 kg을 그 범위의 중간값으로 잡았다(원 명세서
로봇 치수 600×400×300mm와도 어울리는 체급이다). 토크는 바로 비교할 수 있는
표가 마땅치 않아, 실제로 이 체급에서 쓰이는 DDSM350 허브모터의 **최대(피크)
토크 3 N·m**을 그대로 가져왔다 — 정격 1.1 N·m이 아니라 최대값을 쓴 이유는
이 실험의 `wheel_torque_max`가 "순간적으로 낼 수 있는 한계"를 뜻하기 때문이다
(연속 운전 시 발열로 못 버티는 것은 이 실험 범위 밖). **[가정]** 이 숫자들은
실제 로봇 한 대를 역설계한 게 아니라, 위 네 사양을 참고해 "이 체급에서 터무니
없지 않은 값"으로 고른 것이다 — 지수 URDF에 그대로 쓰기 전에 실제 선정
모터 사양으로 다시 확인해야 한다.

## 4. 결론

### (1) V 방식이 질량을 반영하는가

**예상과 다르게, 반영한다.** 처음엔 "DiffDrive는 속도를 명령하는 소스라 질량과
무관하게 명령한 속도를 그대로 만들어낼 것"이라고 예상했다. 하지만:

- **normal(가속도 1.0 m/s² 제한)에서는** 실제로 질량과 무관하다(0kg→25kg 제동거리
  0.5027m→0.5033m, 변화 0.1%). 여기서는 "감속도 자체를 고정"하므로 질량이 끼어들
  자리가 없다 — DiffDrive의 `max_linear_acceleration` 설정이 모터 토크보다 훨씬
  낮아서(필요 토크가 토크 한계 안에 항상 들어옴), 질량이 늘어도 그 고정 감속도를
  그대로 만들어낼 여유가 있다.
- **emergency(가속도 제한 없음)에서는** 질량이 뚜렷하게 반영된다(0kg→25kg 제동거리
  0.2539m→0.4623m, **1.82배**). 원인을 찾아보니 — DiffDrive가 속도를 "명령"하긴
  하지만, 그 명령을 실제로 만들어내는 바퀴 조인트에 **`<limit effort="3.0">`을
  선언해 뒀다**(이 실험의 `wheel_torque_max`). Fortress(DART)는 속도로 구동되는
  조인트라도 이 effort 한계를 그대로 적용한다 — 그래서 "속도 소스"라고 해서
  토크가 무한한 게 아니라, **조인트에 선언한 effort 한계가 진짜 상한**이 된다.
  T(JointController) 방식의 emergency 결과(1.83배)와 V의 결과(1.82배)가 거의
  똑같다는 게 이 설명의 직접적인 증거다 — 결국 둘 다 "같은 3N·m 한계에 걸려서
  멈추는 것"이라 구동 방식과 거의 무관하게 같은 결과가 나온다.

**즉, "V냐 T냐"보다 "바퀴 조인트에 현실적인 effort(토크) 한계를 선언했는가"가
질량이 반영되는지를 결정한다.** V 방식이라도 `<limit effort>`를 생략하거나
크게(예: 무한에 가깝게) 두면 emergency 제동거리가 질량과 무관하게 거의 0에
가까워질 것이다(명령한 속도를 즉시 만들어낼 수 있으므로). 지수 URDF에
`<limit effort>`가 제대로 들어있는지 반드시 확인해야 하는 이유다.

### (2) T 방식 emergency 제동거리의 적재 민감도

0kg 대비 25kg 배율 **1.83배** (0.2548m → 0.4666m). 이론상 배율(토크 식 그대로)은
1.893배이므로 실측이 이론과 3% 이내로 맞는다. 적재 25kg(본체의 거의 전부에
해당하는 질량)을 실으면 급정지 제동거리가 거의 2배가 된다는 뜻이라, **의미
있게 큰 차이**다(목적 2의 답) — 로봇 전방 안전거리를 "빈 상태" 기준으로만 잡으면
안 되고, 최대 적재 상태(이 실험 기준 0.47m + 여유)로 잡아야 한다.

### 문제가 있었으면 원인과 대처

- **gz-transport 네트워킹 일시 정지**: 트라이얼마다 모델을 지우고 다시 스폰하는
  과정에서 한 번 `NodeShared::RecvSrvRequest ... Host unreachable` 오류가 반복
  되며 스크립트가 멈췄다. `ign service --timeout`은 응답 대기 시간일 뿐 CLI
  프로세스 자체가 멈추는 걸 막지 못해서, Python `subprocess.run`에도 명시적
  타임아웃(10~15초)을 걸고 실패 시 예외로 떨어지게 고쳤다. 추가로 트라이얼마다
  최대 3회(재시도 때마다 대기 시간을 늘림)까지 재시도하고, 그래도 실패하면
  해당 행을 `FAILED: ...`로 CSV에 남기고 다음 트라이얼로 넘어가게 했다 - 수정
  후 재실행에서는 80개 전부 재시도 없이 통과했다.
- **T 모드 normal 정지 램프가 시뮬레이션 시각이 아니라 벽시계 속도로 진행되는
  버그**: 이 월드는 `real_time_factor: 0`(스로틀 없음)으로 실시간보다 훨씬
  빠르게 돈다. 변환 노드가 rclpy `create_timer`(+ `use_sim_time` + `/clock`
  구독, 표준적인 방법)로 램프를 걸었는데도 실측에서 벽시계 속도로 진행되는
  것을 발견했다(1.0 m/s² 램프가 시뮬레이션상 10초 넘게 걸림). `/clock` 메시지
  두 개의 시각 차를 직접 계산해 램프를 갱신하도록 바꿔 해결했다(구현 노트 참고).
  이걸 못 잡았으면 T/normal 제동거리가 실제보다 몇 배 크게 나와서 3절 표가
  완전히 틀렸을 것이다.
- **슬립은 거의 없었다**: 80회 중 2회만 경계값(15%) 근처에서 일시적으로
  감지됐다(V/emergency 0kg 1회, T/emergency 2kg 1회) - 둘 다 단발성이고 같은
  조건의 나머지 4회는 슬립 없이 거의 같은 제동거리를 냈다. 바닥 마찰(mu=1.0,
  구동 바퀴 vs 바닥 mu=0.7) 조합에서는 이 속도(1m/s)·질량(≤28+25kg) 범위에서
  구름 접촉이 거의 안 깨진다는 뜻으로 해석한다.

## 구현 노트

### 구동 방식 2가지

| | V (DiffDrive) | T (JointController 힘 모드) |
| --- | --- | --- |
| 명령 | 몸체 속도 (`/cmd_vel`) | 바퀴 각속도 목표 (`scripts/cmd_vel_to_wheel_torque.py`가 변환) |
| 가속 한계 | DiffDrive 플러그인 설정값(`max_linear_acceleration`) | 변환 노드가 소프트웨어로 램프 |
| 제동 한계 | 없음(속도 소스가 그대로 반영) | `cmd_max`/`cmd_min` = ±`wheel_torque_max` |
| normal/emergency 구분 방법 | **다른 스폰**(가속 한계 태그를 통째로 넣거나 뺌) | **같은 스폰**, 변환 노드의 `ramp_limited` 파라미터만 다름 |

V는 가속 한계가 플러그인 SDF 설정값이라 나중에 토픽으로 바꿀 수 없다 — normal과
emergency마다 다시 스폰해야 한다. T는 토크 한계(`cmd_max`/`cmd_min`)가
normal/emergency 공통(둘 다 하드웨어 한계는 같다)이고, 차이는 "변환 노드가
속도 목표를 얼마나 급하게 바꾸는가"뿐이라 스폰은 한 번만 해도 된다.

### 트라이얼마다 다시 스폰하는 이유

Gazebo의 world control reset(`/world/<world>/control`, `reset: {all: true}`)은
**월드가 처음 로드됐을 때의 스냅샷**으로 되돌리는 것이라, `ros_gz_sim create`로
나중에 추가한 모델에는 적용되지 않는다 — 실측으로 확인했다(리셋 후에도 로봇이
구르던 자리 근처에 남아 있었다). 그래서 트라이얼마다 모델을 지우고
(`/world/<world>/remove`) 처음 위치에 다시 스폰한다. 느리지만(트라이얼당 1~2초
오버헤드) 확실하다.

### GT 속도는 위치를 직접 미분

`OdometryPublisher`가 내는 `twist` 필드는 내부적으로 이동평균을 걸어서 급가속·
급정지 구간에서 늦게 반응한다. `accel_time_s`·`braking_distance_m`은 반응
속도가 중요한 측정값이라, `pose.pose.position`만 쓰고 연속한 두 메시지 사이의
변위를 헤더 타임스탬프(시뮬레이션 시각)로 나눠 속도를 직접 계산한다.

### 시뮬레이션 시각 vs 벽시계

이 월드는 `real_time_factor: 0`(스로틀 없음)으로 돈다 - 실시간보다 훨씬 빠르게
진행된다. 측정 스크립트의 모든 타이밍 판단(가속 도달, 1초 유지, 제동 완료)은
GT odom 메시지의 헤더 타임스탬프(시뮬레이션 시각)를 기준으로 한다 — 벽시계
`sleep()`을 쓰면 실제로 몇 초가 지났는지가 의미 없어진다.

이 때문에 실제로 버그를 하나 잡았다: `cmd_vel_to_wheel_torque.py`(T 모드
normal stop의 가속도 제한 램프)가 처음에 rclpy의 `create_timer`(벽시계 기준)를
썼는데, `use_sim_time` 파라미터 + `/clock` 구독으로 시뮬레이션 시각을 쓰게
하는 표준 방법을 적용해도 여전히 벽시계 속도로 램프가 진행되는 것을
실측으로 확인했다(1.0 m/s² 감속이 시뮬레이션상 10초 넘게 걸림). 원인을 더
깊이 파기보다, GT 위치 미분과 같은 방법으로 직접 해결했다: `/clock` 메시지
두 개의 시각 차를 직접 계산해 그 dt로 램프를 갱신한다(rclpy 타이머·시계 내부
동작에 기대지 않음). 수정 후 실측: 1.0 m/s에서 1.0 m/s² 램프가 시뮬레이션
시각 기준 0.996초에 0으로 도달 - 의도한 값과 거의 정확히 일치했다.

### 미끄러짐(슬립) 감지

`JointStatePublisher`로 바퀴 각속도를 받아 `wheel_radius × 각속도`(바퀴 표면
속도)를 GT 속도와 비교한다. 두 값이 (속도가 0.2 m/s를 넘는 구간에서) 15% 이상
벌어지면 슬립으로 기록한다(`results.csv`의 `slipped` 열). V 모드는 바퀴
각속도가 명령값에 그대로 묶이는 속도 소스라 설계상 슬립이 거의 안 생겨야
하고, T 모드는 토크가 포화되는 급정지(emergency)에서 무거운 적재일수록
슬립이 생길 여지가 있다 - 실제 결과는 3절 표 참고.

## 실행 방법

```bash
# 컨테이너 안에서 (docker-compose.yml에 experiments/가 마운트돼 있지 않으면
# docker compose run에 -v 로 추가한다. 예:
#   docker compose run --rm -v "<레포 절대경로>/experiments:/ros2_ws/experiments" dev
cd experiments/payload_braking
python3 scripts/run_experiment.py
```

약 80개 트라이얼(적재 4종 × 5회 × 구동방식 2종 × 정지방식 2종)을 자동으로
돌리고 `results.csv`에 누적 저장한다(트라이얼마다 파일을 다시 써서, 중간에
멈춰도 그때까지 결과는 남는다).

단일 로봇을 눈으로 확인하려면:

```bash
ros2 launch launch/world.launch.py gui:=true   # noVNC 화면에서
xacro model/robot.urdf.xacro payload_kg:=10 drive_mode:=T -o /tmp/robot.urdf
ros2 run ros_gz_sim create -file /tmp/robot.urdf -name amr_payload -x -20 -y 0 -z 0.05
```
