# 연구 2 RL Gazebo 평가 환경 확인 (3주차 작업 11)

연우 2D 학습 환경([research2](../research2/README.md))과 같은 시나리오를 Gazebo(`amr_gazebo` `rl_eval.launch.py`)에서 돌리고, **같은 정책**을 두 환경에 넣어 에피소드마다 결과를 비교했다. 학습한 PPO를 Gazebo에서 다시 잴 때 "2D와 Gazebo가 얼마나 같은 문제인가"를 먼저 보는 실험이다.

## 방법

- 시나리오: 평가 목록 0의 에피소드 0–9, S1(돌발 장애물)·S2(정밀 정지) 강제 (2D `evaluate.py`와 같은 규칙)
- 질량 0·10·25 kg. Gazebo는 질량마다 다시 띄운다 (URDF `payload_mass`, DiffDrive 가속 상한을 풀어 바퀴 토크 한계 3 N·m가 가감속을 정함)
- 정책 `brake` (`amr_gazebo/rl_policies.py`): 출발 속도로 중심선을 따라가다 목표 앞에서 토크 한계 감속으로 서고, 진행선 앞 장애물이 제동 거리 안이면 급정지. **비교군이 아니라 환경 확인용 시험 주행기**다
- 2D는 같은 함수를 `run_2d.py`로 2D 환경 상태에 붙여 돌리고 지표는 2D `evaluation.run_episode` 그대로다
- 총 Gazebo 60회, 2D 60회 (질량 3 × 에피소드 10 × S1·S2). Gazebo는 10/11·10/14 두 번 돌렸다 (Gazebo끼리 재현성)
- 급정지 측정 (`mode:=brake_sweep`): 시나리오 없이 직선에서 0.5·1.0·1.5·2.0 m/s로 달리다 출발선에서 0 명령, 질량·속도마다 3회 (36회)

```bash
bash experiments/rl_gazebo_eval/run_gazebo.sh 10 brake      # Gazebo 60회 + 2D 60회 + 비교 (컨테이너, 2D는 gymnasium 필요)
bash experiments/rl_gazebo_eval/run_brake_sweep.sh 3        # 속도별 급정지 36회 + 요약
python3 experiments/rl_gazebo_eval/compare.py results_gazebo.csv results_2d.csv
python3 experiments/rl_gazebo_eval/brake_sweep.py results_brake.csv
```

- **Gazebo는 항상 모델보다 더 가고, 속도가 빠를수록 차이가 커진다** (0.5 m/s 1 cm 안 → 2.0 m/s 6–11 cm). 속도와 상관없이 같은 차이는 없다
- 차이는 두 가지로 나뉜다
  - **바퀴 회전 관성 (절반쯤, 원인 확인됨)**: 감속 구간 기울기가 모델보다 2.5–5 % 작다. 토크가 몸체뿐 아니라 바퀴(원통 1.5 kg × 2, r 0.1 m → 등가 질량 1.5 kg) 회전도 멈춰야 해서다. 2D 식에 1.5 kg을 더한 값(1.97·1.48·1.08)이 측정값과 0.01 m/s² 안에서 맞는다. v²에 비례하고, 1.5 m/s에서 2.8 cm
  - **명령 지연 (나머지)**: 관성 몫을 빼고 남은 거리를 v로 나누면 6–29 ms다. 0·10 kg에서는 빠를수록 커지고(1.5 m/s 이상 20–30 ms), 25 kg는 10 ms 안팎이다. 2.0 m/s에서는 같은 조건 3회 사이에도 5–19 cm로 흔들린다
- 10/11 측정의 "제동 거리 +6–8 cm"는 1.5–1.7 m/s에서 이 두 몫의 합(4–7 cm)과 크기가 맞다. 짝마다 보면 위 흔들림 때문에 한 방향이 아니었다

### 2D에 반영할지 (리뷰 2, 연우와 정할 일)

- **바퀴 관성은 2D에 넣는 것을 제안한다.** 원인이 분명하고 체계적이다. `dynamics.max_linear_accel`의 질량에 바퀴 등가 질량 1.5 kg을 더하면 된다 (감속이 0 kg 5 %, 25 kg 2.7 % 줄어듦)
- 명령 지연(10–30 ms)과 실행마다의 흔들림은 2D에 정확히 넣기 어렵다. 결과에 "관성을 반영해도 Gazebo가 1.5 m/s에서 2D보다 1.5–4 cm 더 밀리고, 같은 에피소드도 실행마다 최대 15 cm 달라진다"라고 적고, Gazebo 평가는 같은 에피소드를 여러 번 돌려 평균 내는 쪽을 제안한다

원본: [results_gazebo.csv](results_gazebo.csv), [results_2d.csv](results_2d.csv), [results_brake.csv](results_brake.csv). 에피소드 CSV는 2D `episodes.csv`와 열 이름이 같고, Gazebo 실측 열(`popout_gap_actual`, `start_speed_actual`, `popout_place_error`, `valid`, `attempts` 등)이 더 있다.

### 고친 것

- 첫 실행에서 S1 결과가 60 %만 같았다. 비킨 장애물이 Gazebo 통로 벽에 막혀 통로 안에 남았기 때문이다 (2D는 장애물이 벽을 지나간다). 장애물과 벽의 충돌 비트마스크를 나눠 장애물이 벽을 지나가게 했다 (로봇은 둘 다와 부딪힘)
- 장애물 옮기기(`set_pose`)가 실패해도 그냥 넘어갔다 (#144 리뷰 4). 나타난 순간 장애물 GT가 옮길 자리에서 3 cm 넘게 떨어져 있으면 무효로 보고 2번까지 다시 한다. `compare.py`는 무효 에피소드를 뺀다

## 한계·다음

- 정책 관측은 2D처럼 GT다. 카메라·LiDAR로 장애물을 보는 것은 아니다
- 돌발 장애물은 트리거 1.5 m 앞에서 미리 제자리에 옮겨 둔다. 그 사이 LiDAR에는 보인다 (관측은 GT라 정책에는 안 보임)
- Gazebo는 실시간의 약 0.5배라 에피소드당 15 s 정도 걸린다 (2D는 수천 스텝/s). 평가 전용이다
- 학습한 PPO 연결: 정책 함수(obs dict → v, ω)로 감싸 `policy:=모듈:함수`로 넣는다. obs dict → 48차원 관측 변환은 연우와 같이 만든다 (`env._observe`와 같은 식)
